\section{Keyboard input: userspace UART driver}

In milestone 3 we implemented a terminal service that allows any process to write
characters to the console via \co{aos_rpc_serial_putchar}. To support the shell, we also
need to be able to read characters typed by the user. This requires a userspace driver
for the LPUART3 serial port, which is the port wired to the serial-to-USB converter on the
Toradex board.

\subsection{Device drivers}

Two drivers are required. The \textbf{GIC distributor} driver (\co{usr/drivers/gic_dist/})
configures the ARM Generic Interrupt Controller so that a given interrupt line is forwarded
to a specific CPU core. The \textbf{LPUART} driver (\co{usr/drivers/lpuart/}) provides
\co{lpuart_init}, \co{lpuart_putchar}, \co{lpuart_getchar} and \co{lpuart_enable_interrupt}.
Both drivers require their device register regions to be mapped read/write with caching disabled.
Since \co{init} is the most privileged userspace process, it can forge \co{DevFrame} capabilities
for arbitrary physical addresses and map them itself:

\begin{lstlisting}
struct capref frame;
slot_alloc(&frame);
devframe_forge(frame, IMX8X_GIC_DIST_BASE, IMX8X_GIC_DIST_SIZE, 
               my_core_id);
paging_map_frame_attr(get_current_paging_state(), &gic_base,
                      IMX8X_GIC_DIST_SIZE, frame,
                      VREGION_FLAGS_READ_WRITE_NOCACHE);
\end{lstlisting}

\medskip\noindent
The same procedure is applied to \co{IMX8X_UART3_BASE} for the LPUART registers.

\subsection{Interrupt Chain Setup}

The full initialization sequence follows the ordering required by the hardware. The interrupt
handler must be registered before the interrupt is enabled, so that no interrupt arrives
while the system is unprepared to handle it.

\begin{enumerate}
  \item Initialize the GIC distributor driver with its mapped register base.
  \item Initialize the LPUART driver with its mapped register base.
  \item Use \co{inthandler_alloc_dest_irq_cap} to allocate an \co{IRQDest}
        capability for UART3's interrupt vector (260), then register
        \co{uart_irq_handler} on \co{init}'s default waitset via
        \co{inthandler_setup}.
  \item Enable the interrupt in the GIC distributor:
\begin{lstlisting}
gic_dist_enable_interrupt(gds, IMX8X_UART3_INT, 0x1 /* cpu0 */, 0);
\end{lstlisting}
  \item Enable the receive interrupt in the LPUART:
\begin{lstlisting}
lpuart_enable_interrupt(g_lpuart);
\end{lstlisting}
\end{enumerate}

\medskip\noindent
When a key is pressed, the LPUART hardware fires IRQ 260, the GIC forwards it to
CPU 0, and the CPU driver delivers an LMP message to the \co{IRQDest} endpoint.
This wakes \co{uart_irq_handler} on \co{init}'s waitset.

\subsection{Ring Buffer and Deferred RPC Replies}

The interrupt handler drains all available characters from the LPUART into a 256-byte
ring buffer:

\begin{lstlisting}
static void uart_irq_handler(void *arg) {
    char c;
    while (lpuart_getchar(g_lpuart, &c) == SYS_ERR_OK) {
        if (pending_reader != NULL) {
            cs_send3(pending_reader, NULL_CAP, AOS_RPC_MSG_CHAR_RESP, ...);
            pending_reader = NULL;
        } else {
            buf_push(c);
        }
    }
}
\end{lstlisting}

\medskip\noindent
When a process calls \co{aos_rpc_serial_getchar}, \co{init} receives the LMP message
in \co{handle_getchar} and calls \co{uart_service_getchar(cs)}. If a character is already
buffered, the reply is sent immediately. Otherwise, the \co{client_state} pointer is parked
as \co{pending_reader} and the reply is deferred until the next interrupt fires. This avoids
blocking \co{init}'s event loop. On QEMU, where there is no LPUART, the implementation falls
back to \co{sys_getchar}.

\section{RamFS file system support}
We route all RamFS file operations through the \co{init} process. Each core has its own
in-memory file system. In order to support this we add file system functionality to
our RPC implementation. We add the following calls to the \co{aos_rpc} API:
\begin{lstlisting}
errval_t aos_rpc_fs_open(struct aos_rpc *chan, const char *path, int flags,
                         fs_fhandle_t *ret_handle);

errval_t aos_rpc_fs_close(struct aos_rpc *chan, fs_fhandle_t handle);

errval_t aos_rpc_fs_read(struct aos_rpc *chan, fs_fhandle_t handle,
                         void *buf, size_t nbytes, size_t *bytes_read);

errval_t aos_rpc_fs_write(struct aos_rpc *chan, fs_fhandle_t handle,
                          const void *buf, size_t nbytes, size_t *bytes_written);

errval_t aos_rpc_fs_seek(struct aos_rpc *chan, fs_fhandle_t handle,
                         enum fs_seekpos whence, off_t offset);

errval_t aos_rpc_fs_stat(struct aos_rpc *chan, fs_fhandle_t handle,
                         struct fs_fileinfo *info);

errval_t aos_rpc_fs_mkdir(struct aos_rpc *chan, const char *path);

errval_t aos_rpc_fs_rmdir(struct aos_rpc *chan, const char *path);

errval_t aos_rpc_fs_remove(struct aos_rpc *chan, const char *path);

errval_t aos_rpc_fs_opendir(struct aos_rpc *chan, const char *path,
                            fs_fhandle_t *ret_handle);

errval_t aos_rpc_fs_closedir(struct aos_rpc *chan, fs_fhandle_t handle);

errval_t aos_rpc_fs_readdir(struct aos_rpc *chan, fs_fhandle_t handle,
                            char **ret_name, struct fs_fileinfo *info);

\end{lstlisting}
The corresponding handlers are added to \co{rpc_server.c} and message tags to \co{aos_rpc.h}. The shell (or user process) can specify 
specify the flags which they want the file to be opened with, and can embedd the core which they
prefer to create the file on by passing \co{FS_OPEN_ON_CORE(core) | FS_OPEN_CREATE} to \co{aos_rpc_fs_open()} as the \co{flags} argument. This is intended to mirror
the spawn procedure of allowing a user to specify the core to spawn the procedure on (in the future, the shell does not currently support this). Any process can access files on any core, this is implemented with UMP redirection. To facilitate
demultiplexing file operations to the correct core, we embed the core in the \co{fs_handle_t} in the same manner
that the core of a process is embedded in its pid. Via this mechanism, \co{init} can route the operation to the correct
core without intervention from the user. One important constraint is that a user must supply the \co{FS_OPEN_ON_CORE(core)} flag to access 
cross core files (even when not creating them). This is because file systems on different cores do not share a namespace. This is 
an area for future work as the current implementation pushes some burden to the user.
\section{Pipes and I/O redirection}
To enable I/O redirection we change the spawn and RPC infrastructure. Processes are spawned
with information about where their input and output flows, then \co{aos_rpc_serial_getchar/putchar} correctly
routes characters (TODO: line granularity not characters) to the correct endpoint. Piping I/O between processes works 
in the following manner:
\begin{enumerate}
  \label{pipe_steps}
  \item The shell first creates and allocates a capability for the frame:
  \begin{lstlisting}
  struct capref pipe_frame;
  size_t pipe_size;
  frame_alloc(&pipe_frame, 2 * BASE_PAGE_SIZE, &pipe_size);
  \end{lstlisting}
  \item The shell then creates an \co{io_config_frame} for each side of the pipe and
  spawns the processes:
  \begin{lstlisting}
  // This omits the reader setup but it is nearly identical (the reader just sets pipe_in true and pipe_out_is_dsp 0)
  struct io_config_frame cfg = {
    .pipe_out        = true,
    .pipe_out_is_bsp = 1,
    .pipe_out_bytes  = pipe_size,
  };
  aos_rpc_proc_spawn_with_io(rpc, "writer_bin", core, pipe_frame, &cfg, &pid1);

  \end{lstlisting}
  \item Based on \co{core}, the correct \co{init} receives this \co{aos_rpc} call, and parses the configuration.
  \item \co{init} then creates a new frame for the IO config info and maps it into its virtual address space.
  \item \co{init} then assembles a capability array with capabilities to the pipe frame to pass to the spawned processes.
  \item \co{init} then spawns the process with \co{spawn_cmdline_with_caps()} which places the capabilities in the childs CSpace.
  \item In the new process, \co{barrelfish_init_onthread()} is called which does the necessary capability operations to map the pipe frame into its VSpace.
  \item This fills in a global variable identifying if I/O is piped or directed to a file.
  \item \co{aos_rpc_serial_getchar/putchar} correctly writes to the pipe rather than calling \newline \co{sys_putchar/getchar}.
\end{enumerate}
For file redirection the process is much the same except, fields are simply set in the \co{io_config_frame} that hold
\co{fs_handle_t} for the input and/or output file, no capability operations have to occur and are skipped with \co{NULL_CAP} checks. 
\section{Synchronizing serial input \& output}
Serial input is synchronized with RPC. Because the UART driver is an RPC service, we trivially synchronize
by making \co{bsp_init} the only process with a UART driver. All calls that do not come from core 0 are routed through UMP
to core 0. Because \co{init} is single threaded this means that only one request to the driver is handled at once. Serial output 
synchronization between arbitrary processes is not broadly implemented. The shell itself uses a mutex to guard access to the 
serial out which ensures that all threads in the shell access the shell sequentially. Background processes output are only printed
once they complete. 

\section{Command processing}
See \hyperref[appA]{Appendix A} for the full list of commands supported. Commands are processed in an infinite loop which reads serial input, parses the
input into tokens, and then dispatches to the correct handler based on the command.
All commands are implemented as builtins. We wrap commands in a structure which stores
the name of any files to be used as input or output. For \cl{$ run} and \cl{$ oncore} redirecting
this I/O is already handled, but because builtins are not their own processes, output is not correctly
routed through RPC, so files are manually written. To handle pipes we create a structure which can 
hold a reader and a writer command and correctly spawn the processes using the steps outlined \hyperref[pipe_steps]{above}.
Commands on either side of the pipe must be either \cl{run} or \cl{oncore} but any combination is 
possible. Files can only be used as input on the left side of the pipe and output on the right side of the pipe,
with violation of this causing an error to print. 

\subsection{Environment variables}
In order to facilitate \cl{$!} or \cl{$?} we store global variables in the shell for the last background
pid and the last foreground exit code. When tokenizing we simply read these variables and replace the env variables
with the local values. We also add support for the shell storing a current working directory. This allows us
to create absolute paths from relative paths and support the commands \cl{$ pwd}, \cl{$ cd}. This is 
mainly an ergonomic feature but it aids in user immersion and the support of relative paths is immense for 
usability. 


\subsection{Background tasks}
In order to support background tasks, rather than calling dispatch in our loop, we create a new thread whose 
entry point is \co{background_task()}. This function is a wrapper around dispatch which simply prints 
the background task number and the command (or pid if the underlying command is \cl{run} or \cl{oncore}).
We redirect the output of the command into a temp file, so it can be printed atomically upon completion. We
then call dispatch on the underlying command and wait for it to complete via RPC. We then acquire the output mutex and \cl{cat} the tempfile
and print out that the background task is done before releasing the mutex and exiting. We believe this provides
a better user experience than bash because terminal output is not garbled.

\section{Development process}
Shell development started when Shane implemented the infrastructure needed for file system 
operations over RPC, as well as the code which enables spawning processes with redirected I/O. Sahil
then wrote the UART driver and Shane and Sahil implemented all remaining shell functionality. Testing 
and debugging was done mainly adhoc (other than piping which was independently tested) via experimentation
in the shell environment, and we recognize
that there are many scenarios we cannot test this way. Additionally, some functionality shortcuts were taken such as
only implementing file redirection for a subset of commands.
